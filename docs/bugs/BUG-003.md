# BUG-003 — Project ID inconsistente: 77 tests fallaban con 401 por `aud` mismatch

- **Severidad:** crítica (para el workflow de QA)
- **Prioridad:** alta
- **Entorno:** local (emulador Firestore + Auth)
- **Estado:** ✅ RESUELTO en `48ff6d4` (16 nov 2026)
- **Descubierto por:** corrida de la suite Go con emulador → 77 fallos

## Pasos para reproducir (antes del fix)

1. Levantar el emulador **como dice la documentación**:

   ```bash
   npx --yes firebase-tools emulators:start \
     --config firebase.emu.json --project demo-test --only firestore,auth
   export FIRESTORE_EMULATOR_HOST=127.0.0.1:8090
   export FIREBASE_AUTH_EMULATOR_HOST=127.0.0.1:9098
   export GCP_PROJECT_ID=demo-test
   ```

2. `cd backend && go test ./... -count=1`
3. **77 tests fallan**:

   ```
   Aviso: token inválido para test-push-1794856616486954454: ID token has
   invalid 'aud' (audience) claim; expected "test-turnobot" but got "demo-test"
   --- FAIL: TestPushTokenRegistro (0.03s)
       handlers_test.go:3086: vacío code=401, esperaba 400
   --- FAIL: TestMoverSlotOcupadoYLibre (0.05s)
       handlers_test.go:3122: book 10:00 code=401, esperaba 201
   ... (77 en total)
   ```

## Esperado

Todos los tests de integración pasan contra el emulador.

## Actual

El 401 `login_requerido` no es del handler: el token **sí** es válido para el
emulador, pero el SDK de Auth del backend está configurado con un project ID
distinto al que emitió el token.

## Causa raíz

**Dos convenciones de project ID conviviendo en el repo:**

| Fuente | Project ID |
|--------|-----------|
| `docs/PLAN_QA.md` §9.1, §9.2 | `demo-test` |
| `docs/QA_ENTORNOS.md` | `demo-test` |
| `docs/QA_GUIDE.md` | `demo-test` |
| `backend/seed.go` | `demo-test` |
| `scripts/run-qa.sh` (`--local`) | `demo-test` |
| `frontend/e2e-tests/target.js` | `demo-test` |
| `frontend/e2e-tests/cleanup-staging.mjs` | `demo-test` |
| `README.md` | `demo-test` |
| **`backend/gcp_test.go:40`** | **`test-turnobot`** ← el outlier |
| **`harness.sh`** | **`test-turnobot`** ← el outlier |

El `aud` de un ID token de Firebase es el project ID. `testAuthClient` crea el
app de Firebase con `testProjectID()` y `VerifyIDToken` compara el `aud` del
token contra ese project ID. Con el emulador en `demo-test` y el SDK en
`test-turnobot`, **todos** los tests que requieren token fallan con 401.

Peor: `harness.sh` sí usaba `test-turnobot` (coherente consigo mismo), así que
el harness "funcionaba" y el resto del repo no. Dos mundos separados que
nunca se cruzaron.

## Evidencia

Baseline medido con `git stash` (código sin mis cambios, mismo emulador):

```
$ git stash push -u -- backend turnobot-test-learn harness.sh
$ go test ./... -count=1 | grep -c "^--- FAIL"
77
```

Después del fix, mismo emulador, mismo comando:

```
$ go test ./... -count=1
ok   turnobot   17.9s
$ go test ./... -count=1 | grep -c "^--- FAIL"
0
```

## Impacto

- **A quién afecta:** a todo el que siga la documentación al pie de la letra.
  Es el camino documentado, no un caso raro.
- **Cuánto:** 77 de 104 tests de integración (74 %). Imposible usar la suite
  como evidencia sin conocer el truco.
- **Gravedad real:** **es el peor tipo de bug de entorno**, porque el mensaje
  (`401`, `invalid 'aud'`) parece un problema de autenticación del negocio y
  no del proyecto ID. Un QA junior puede perder días buscando un bug de auth
  que no existe.

## Nota

¿Reproducible? **Siempre**, si se sigue la documentación. Intermitente solo si
alguien se acuerda de exportar `test-turnobot` a mano.

## Fix aplicado

1. `testProjectID()` ahora devuelve `demo-test` (la convención del repo) y
   acepta override con `QA_EMULATOR_PROJECT_ID`.
2. `harness.sh` usa `EMU_PROJECT` (default `demo-test`) para el emulador, el
   backend y los tests — una sola variable para los tres.
3. `harness.sh` ahora exporta `FIREBASE_AUTH_EMULATOR_HOST` (no lo exportaba:
   los tests que necesitan Auth se omitían en silencio).

## Lección

**El entorno de pruebas es código de producción.** Merece la misma regla que
el resto: una fuente de verdad, valores por defecto consistentes, y una
prueba que falle si alguien los cambia. Un `project ID` que aparece escrito
literal en 8 lugares distintos *es* un bug esperando.

Extra: hoy existe `docs/QA_ENTORNOS.md` con la tabla de troubleshooting que
ya mencionaba `ID token has invalid 'aud'` → *"Project ID del backend/Auth no
es demo-test"*. **El síntoma ya estaba documentado; la causa raíz no.** Y el
fix correcto no era documentar más, era eliminar la segunda convención.
